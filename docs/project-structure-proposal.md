# Предложение по структуре проекта

## 1) Что стоит изменить сейчас

1. **Добавить слоистую архитектуру** (`api` → `services` → `core`/`models`), чтобы бизнес-логика не смешивалась с HTTP-слоем.
2. **Вынести промпты в отдельную директорию** (`src/prompts`), чтобы их можно было версионировать и тестировать отдельно.
3. **Разделить тесты по уровням** (`unit`, `integration`, `e2e`) и сразу настроить базовые проверки.
4. **Добавить директорию `config`** для шаблонов конфигурации и дефолтных настроек.
5. **Заложить `scripts/`** для типовых команд разработки (локальный запуск, тесты, линт).

## 2) Рекомендуемая целевая структура

```text
src/app/api/         # роуты, контроллеры, схемы запросов/ответов
src/app/services/    # сценарии использования (use-cases)
src/app/core/        # доменная логика, валидаторы, правила
src/app/models/      # модели данных
src/prompts/         # шаблоны промптов, системные инструкции
tests/unit/          # быстрые изолированные тесты
tests/integration/   # тесты интеграции с БД/LLM-провайдерами (с моками)
tests/e2e/           # сквозные сценарии
config/              # yaml/json-конфигурация
scripts/             # повторяемые dev-скрипты
```

## 3) Минимальные шаги внедрения (итерация 1)

- Создать каркас директорий `src`, `tests`, `config`, `scripts`.
- Зафиксировать единый формат конфигурации (`.env` + `settings.yaml`).
- Подключить базовые инструменты качества:
  - форматирование (например, `ruff format`),
  - линт (`ruff check`),
  - тесты (`pytest`).
- Добавить CI pipeline с тремя стадиями: lint, test, build.

## 4) Важные инженерные договорённости

- Внешние интеграции (LLM API, хранилища, очереди) прятать за адаптерами.
- Не хранить промпты внутри кода сервисов — только ссылки на файлы.
- Для каждого нового сценария генерации отчёта создавать:
  - use-case в `services`,
  - unit-тест,
  - e2e-тест на основной пользовательский поток.
